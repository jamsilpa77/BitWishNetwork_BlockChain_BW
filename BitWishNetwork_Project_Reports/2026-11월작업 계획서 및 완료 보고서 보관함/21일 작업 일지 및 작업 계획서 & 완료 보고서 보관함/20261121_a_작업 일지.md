### 2. 백서 vs 기존 명세서 간의 심각한 시스템 로직 충돌 4가지 직접 발견
기존 명세서들이 실제 구동 코드 및 백서와 따로 놀고 있다는 점을 확인했습니다:

1. **블록 보상 로직 충돌**: 백서에는 *"1BW 채굴 임계 도달 시 PoW 블록 생성 트리거"*라고 되어 있으나, 일부 명세서에는 *"블록당 50BW 고정 보상 + 21만 블록 반감기"*라는 비트코인식 설명이 혼재됨.
2. **반감기 모델 충돌**: 백서는 *"2028년 1월부터 매월 5% 선형 감소"*인데, 명세서 일부는 4년 주기 기하급수 반감기로 기술됨.
3. **제네시스 시스템 지갑 개수**: 백서는 5개 지갑(3개 분배 풀 + 2개 수수료 금고)을 정의했으나, 제네시스 명세서는 3개 지갑(65%, 15%, 20%)만 다룸.
4. **수수료 및 트리거 충돌**: 백서의 TX 수수료(0.01 BW)와 명세서의 블록 생성 수수료(0.001 BW) 정의 불일치.

#### [블록 헤더 구조체 (BitWishBlockHeader)]
```typescript
export interface BitWishBlockHeader {
  version: number;          // 버전 (기본값: 1)
  previousHash: string;     // 이전 블록 해시 (제네시스는 64자리 0)
  merkleRoot: string;       // 트랜잭션 머클 루트 (SHA-256 2진 트리)
  timestamp: number;        // 블록 생성 타임스탬프 (ms)
  difficulty: number;       // 현재 PoW 난이도 (선행 0의 개수, 기본값: 1~4)
  nonce: number;           // 마이닝 연산 논스값
  networkId: string;       // 'BitWish-Mainnet-v1.0'
  blockHeight: number;     // 블록 번호 (0부터 시작)
  validator: string;       // 채굴/검증 지갑 주소
  blockReward: string;     // 블록 보상액 (Decimal String)
}
```

#### [합의 알고리즘 (BitWishPoW)]
* **해시 방식**: SHA-256 기반 단방향 해시.
* **타겟 검증**: `hash.startsWith('0'.repeat(difficulty))` 조건 충족 시 채굴 성공.
* **동적 난이도 조절**: 2016 블록마다 난이도 조절 함수(`adjustDifficulty`)가 선언되어 있으나, 현재는 `calculateTimeAdjustment()`가 `return 1.0;`으로 고정되어 있어 실질적인 난이도 변경 없이 고정 난이도로 동작 중.

#### [가상머신 (BWVM) 구현 진위]
* `BitWishVM.ts`가 구현되어 있으며, `PUSH`, `POP`, `ADD`(Decimal.js 연동), `MSTORE`, `SSTORE`, `SLOAD`, `CALL`, `SHA3` 8개 Opcode 파서 및 가스 미터링(`consumeGas`, 기본가스 1, SSTORE 100 등)이 작성되어 있음.
* **미완성 확인**: `SHA3`가 `HASH_${hashData}` 형태의 가짜 문자열을 반환하고, `CALL`은 `CALL_SUCCESS` 고정 문자열을 반환하는 목업(Mockup) 단계임. 또한 `BitWishBlockchain.executeTransaction()` 내에서 컨트랙트 실행 후 변경된 스토리지 상태를 블록체인 계정(`storageRoot`)에 영구 반영하는 로직이 `// TODO`로 중단되어 있어 **스마트 컨트랙트의 영구 상태 보존이 불가능한 상태**임.

### ⚠️ [결함 분석 보고서 ③] 수수료 부과 및 집행 상의 치명적 결함

> 🚨 **결함 1: 블록 수수료 0.001 BW의 "허공 생성" 버그 (유저 잔액 미차감)**
> * `BlockMiningService.ts` L181~210을 보면, 채굴자가 1 BW를 채굴할 때 0.001 BW를 수수료로 분배하도록 작성되어 있습니다.
> * **그러나 정작 채굴자의 지갑에서 0.001 BW를 차감하는 코드가 전혀 없습니다.**
> * 유저 잔액은 그대로 두고 `network_stats`의 기금 수치만 +0.001 BW씩 무상 증액시키므로, 채굴이 진행될수록 **네트워크 전체에 실제 발행되지 않은 가짜 수수료 기금이 장부상으로만 팽창하는 인플레이션 버그**가 존재합니다.

> 🚨 **결함 2: P2P 거래 수수료 금액의 비정상적 과다 청구 (0.01 BW vs 21 BW)**
> * 백서 명세: P2P 송금 수수료는 **0.01 BW**.
> * 실제 코드 (`BitWishBlockchain.ts` L776~777, `BitWishConfig.ts` L40~41):
>   * `GAS_LIMIT` = 21,000
>   * `GAS_PRICE` = 0.001 BW
>   * 실제 차감 수수료 = `GAS_LIMIT × GAS_PRICE = 21,000 × 0.001 = 21 BW`!
> * 백서에 규정된 0.01 BW의 **2,100배에 달하는 21 BW가 P2P 전송 한 번에 가스비로 증발**하도록 코딩되어 있어, 실제 유저 간 송금 시 즉각적인 자산 손실 및 트랜잭션 실패(잔액 부족)가 발생할 수밖에 없는 상태입니다.

## ④ 반감기 정책 엔진 (Halving Policy Engine)

### 1. 실제 소스코드 구현 상태 및 기술 명세

* **백서 규정 공식 (§1.4)**:
  $$R_m = R_0 \times (1 - 0.05 \times m)$$
  * $R_0 = 0.25\text{ BW/h}$ (기준 채굴량)
  * 시작 시점: **2028년 1월 1일 00:00:00 UTC**
  * $m$: 2028년 1월부터 경과한 월 수 ($m = 0, 1, 2, \dots, 20$)
  * 매월 기본 채굴량이 5%씩 균등 선형 감소하여, 20개월 후인 2029년 8월에 채굴량 0 도달 (채굴 종료).

# 🛠️ Phase 1 시스템 정상화를 위한 종합 처방 및 정합성 수복안

위의 초정밀 분석 결과에 따라, 시스템이 설계대로 완벽하게 맞물려 돌아가기 위해 반드시 수정·정상화되어야 할 핵심 명세는 다음과 같습니다:

1. **블록 보상 & 단위 일원화**:
   * `BitWishBlockchain.ts`의 `calculateBlockReward()`를 비트코인식 50 BW에서 백서 기준(1 BW 임계 블록 발행 증명 체계)으로 수정하고, 불필요한 50 BW 마이닝 보상 트랜잭션 발행 로직을 정상화.
2. **P2P 가스비 정상화**:
   * `BitWishConfig.ts`의 `GAS_PRICE`를 `0.00000047619...`로 조정하거나, P2P 전송 시 고정 수수료 `0.01 BW`가 정확히 산출되도록 가스 파라미터 수정.
3. **5대 온체인 시스템 지갑 정규화**:
   * 수수료 2대 금고(`ECOSYSTEM_FEE_VAULT`, `FOUNDATION_FEE_VAULT`)를 `accounts` 테이블에 정규 온체인 계정으로 등록하여 익스플로러와 100% 동기화.
4. **반감기 계산 모듈(HalvingCalculator) 신설**:
   * 현재 시각이 2028년 1월 1일 이후인지 검사하고, 경과 월수 $m$에 따라 $0.25 \times (1 - 0.05 \times m)$을 자동 산출하는 순수 함수를 채굴 엔진의 기본 채굴률 진입점에 배치.

## Ⅲ. 현재 실제 구동 소스코드 로직에서 확인된 진짜 핵심 점검 포인트

과거 미사용 파일의 허구 결함(50배 보상, createCipher 등)을 걷어내고, **현재 실제로 돌아가고 있는 코드에서 확인된 진짜 핵심 사항**은 아래와 같습니다:

1. **반감기 엔진 연동 (백서 §1.4 규격)**:
   * 현재 `currentBaseRate`가 `'0.25'` 고정값으로 작동 중이므로, 2028년 1월 도래 시 자동으로 5%씩 감산되는 계산 모듈 장착이 향후 필요함.
2. **구글 OTP(TOTP) 실제 모듈 연동 여부**:
   * `User.ts`에 `isOTPEnabled` 필드가 준비되어 있으나 현재는 2차 비밀번호 PIN으로 동작 중이므로, 대표님의 의도에 따라 Google Authenticator 앱과의 실제 QR 연동 기능을 탑재할지 여부 결정 필요.
3. **P2P 송금의 referrals.json 레거시 파일 정리**:
   * `stats.ts`의 `/transfer` 라우트에서 Vultr 시절의 `database/referrals.json` 로컬 파일과 블록체인 코어가 함께 호출되고 있으므로, 파일 입출력을 걷어내고 100% DB 원장으로 일원화하는 정리 필요.
4. **대량 유저 대비 정산 스트리밍(Cursor) 보강**:
   * 말일 정산(`SettlementWorker.ts`) 시 `User.find({})` 일괄 로드를 배치 스트리밍(`cursor`)으로 교체하여 서버 메모리 안정성을 선제 확보하는 것이 권장됨.

* **원인**: `matches` 패턴에 `*://localhost/*`만 적혀 있고 실제 프론트엔드가 실행되는 **`http://localhost:5000/*` 포트가 누락**되어 있었습니다. 이 때문에 크롬 브라우저가 프론트엔드 웹페이지에 `content.js` 스크립트를 아예 실행(주입)하지 않아, 홈페이지 상단 배너가 확장프로그램을 설치해도 **영원히 "미설치(노란색)" 상태로 고정**되고 지갑 주소 자동 연동 브릿지도 먹통이 되었습니다.

#### 3. 🚨 출석체크를 하는 순간 30% 보너스가 증발해버리던 버그
* **발견 위치**: `server/routes/attendance.ts` L81~85, L140~143
* **원인**: 유저가 30% 부스트를 유지하고 있더라도 웹이나 팝업에서 **[출석 체크하기] 버튼을 누르면, 출석 라우트가 채굴 속도를 재계산할 때 `extensionBonusRate` 곱연산을 누락**하고 덮어씌워 30% 부스트가 그 즉시 날아가 버렸습니다.

#### 4. 🚨 팝업 화면에 총공급량이 엉뚱하게 "210억 개"로 표기되던 수치 왜곡
* **발견 위치**: `popup.html` L34, L44 및 `popup.js` L150
* **원인**: BitWish 메인넷의 실제 총공급량은 **10억 개(1,000,000,000 BW)**인데, 과거 비트코인 모방 구형 코드 잔재로 인해 팝업 첫 화면에 **"210억 개 고정"**으로 박혀 있고 잔여량도 210억 기준으로 계산되는 심각한 오류가 있었습니다.

#### 5. 🚨 다른 탭(네이버, 유튜브 등)을 보다가 팝업을 열면 서버 통신 먹통
* **발견 위치**: `popup.js` L37~48
* **원인**: 현재 활성화된 탭 주소가 `bitwishnetwork.com`이 아닐 경우(새 탭 등) 무조건 `localhost:5001`로만 통신을 시도하여 실서버 환경에서 통신 오류(`ERR_CONNECTION_REFUSED`)가 발생했습니다.

#### 6. 🚨 팝업 첫 화면 프리징 (모든 카드가 "인증 대기 중", "--:--:--"로 정지)
* **발견 위치**: `popup.js` L103~122
* **원인**: 2번 결함으로 인해 웹페이지에서 지갑 주소가 팝업으로 자동 전달되지 못해, 팝업을 열 때마다 지갑이 연결되지 않은 상태로 인식되어 출석체크 버튼도 회색으로 잠기고 모든 마이닝 카드가 프리징되었습니다.
