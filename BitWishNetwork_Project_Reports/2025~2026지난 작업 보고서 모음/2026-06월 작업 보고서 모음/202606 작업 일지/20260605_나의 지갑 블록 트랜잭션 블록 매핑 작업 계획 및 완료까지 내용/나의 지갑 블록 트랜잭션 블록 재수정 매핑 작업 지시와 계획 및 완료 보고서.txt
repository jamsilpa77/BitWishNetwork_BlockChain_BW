전체적인 시스템 규칙, 현재 데이터 상태, 그리고 질문해주신 **"수복 작업을 거쳤음에도 구 채굴 발행 블록 트랜잭션이 사라지지 않고 남아있는
문제"**에 대해 파악한 바를 정리하고, 기술적인 원인과 해결 방안을 설명해 드리겠습니다.

1. 설명해주신 시스템 구조 및 데이터 정합성 이해

  - 가입자 및 추천 관계 (1대1 단대단)
      - 총 가입자 수는 17명이며, 추천인(부모)과 가입자(자식) 간에는 가입 시점에 상호 간에 각각 1 BW씩 보상이 지급됩니다.
      - 추천 코드 없이 가입한 유저는 보상이 전혀 없습니다.
      - 다단계(피라미드) 구조가 아니기 때문에, 자식의 자식이 가입하더라도 그 상위 조부모에게는 추가 보상이 흐르지 않고 당대에서 즉시
        종료됩니다.
  - 2번 스샷 수치 분석
      - 실시간 현재 BW 발행량 (30 BW): 부/자 보상, 자/자 보상, 일반/자 보상 등으로 최종 발행된 총수량이 30 BW임을
        의미합니다.
      - 실시간 생성 블록 (31 블록): 1 BW당 1블록이 생성되어 적재된 30개의 블록과, 최초 시스템 구동 시 생성된 제네시스 0번
        블록(1개)이 합산되어 총 31개의 블록이 표시되고 있습니다.
  - 3번 & 4번 스샷의 유저 케이스 (BW34FE...A626)
      - 이 유저는 본인이 가입할 때 사용한 부모 추천 코드 1개(붉은색)와 본인을 추천인으로 등록하고 가입한 자식 유저 5명(푸른색)을
        두고 있어, 추천 관계에 얽힌 대상이 총 6명입니다.
      - 4번 스샷의 블록 트랜잭션 탭을 보면 가상 높이 #200000(자식 가입 보상 1개)과 #100000 ~ #100004(부모 초대
        보상 5개)로 구성된 "추천 보상" 유형의 트랜잭션이 총 6개 표시되어 추천 이력과 정합성이 맞습니다.

2. 발견된 문제점 분석 (구 채굴 발행 블록이 남아있는 이유)

문제 현상: 블록체인 전체 상태와 채굴 포인트는 정상적으로 초기화되어 실시간 생성 블록이 31개(최대 블록 높이 30번대)로 정상 수복되었으나,
유저의 블록 트랜잭션 목록에는 과거 테스트 중에 생성되었던 높은 블록 번호(예: #74, #70, #69, #65 등)의 "채굴 발행" 데이터가
삭제되지 않고 그대로 출력되고 있습니다.

기술적 원인 분석:

1.  수복 엔진(Healer)의 단방향(Add-only) 설계 한계
      - 명세서 4.1절의 내용을 보면, 물리 블록 동기화 공정은 blocks 컬렉션에 존재하지만 blocktransactions 장부에
        "누락된" 채굴 블록을 찾아 복구하는 방식으로 작동합니다.
      - 즉, "없는 데이터를 채워 넣는 작업(Insert/Upsert)"만 수행할 뿐, **"실제 블록 체인(blocks 컬렉션)에서
        삭제되어 더 이상 존재하지 않는 유실된 블록 트랜잭션을 blocktransactions 컬렉션에서 찾아 지우는
        작업(Cleanup/Delete)"**은 정의되어 있지 않거나 누락되어 있습니다.
2.  테스트 초기화 시 데이터베이스 간의 동기화 불일치
      - 채굴 포인트를 초기화하거나 메인넷의 블록 데이터(blocks 컬렉션)를 31번 블록 이전으로 되돌렸을 때, 지갑의 블록 트랜잭션
        탭이 바라보는 독립적인 데이터 저장소인 blocktransactions 컬렉션 내부의 과거 데이터(type:
        'Minting')들이 일괄 삭제(Truncate)되거나 동기화 처리되지 못했습니다.
      - 그 결과, 네트워크 전체의 실제 블록 수는 31개로 줄었음에도 불구하고 과거 잔재 데이터들이 데이터베이스에 고스란히 유령
        데이터(Orphaned Data)로 남아 화면에 출력되는 현상이 발생한 것입니다.

3. 해결 방안 제시

이 문제를 해결하고 완벽한 정합성을 유지하기 위해서는 수복 엔진 기동 단계 혹은 블록 초기화 유틸리티에 아래와 같은 데이터
청소(Purge/Pruning) 로직을 추가해야 합니다.

  - 해결책 A: 수복 엔진 내 유령 트랜잭션 제거 로직 추가

      - 백엔드 서버가 시작될 때, 실제 blocks 컬렉션에 존재하는 유효한 최대 블록 높이(예: maxBlockHeight = 30)를
        구한 뒤, blocktransactions 컬렉션에서 type: 'Minting'이면서 이 최대 높이를 초과하는 트랜잭션들을
        자동으로 삭제해 주는 정비 단계를 추가합니다.
      - 예시 로직:
        // 1. 현재 blocks 컬렉션의 실제 최대 블록 높이 조회 (예: 30)
        const maxValidBlock = await networkDb.collection('blocks').find().sort({ height: -1 }).limit(1).next();
        const maxValidHeight = maxValidBlock ? maxValidBlock.height : 0;

        // 2. blocktransactions 장부에서 실제 블록 높이를 초과하는 구 채굴 데이터 일괄 삭제
        await networkDb.collection('blocktransactions').deleteMany({
            type: 'Minting',
            blockHeight: { $gt: maxValidHeight }
        });

  - 해결책 B: 초기화(Reset) 프로세스 시 트랜잭션 테이블 일괄 정리

      - 테스트 목적으로 채굴 포인트 및 블록 데이터를 초기화하는 시점에, blocktransactions 컬렉션에서 type:
        'Minting' 데이터 전체를 먼저 비워버린(deleteMany({ type: 'Minting' })) 후 수복 엔진을
        돌려 1~30번 블록만 깔끔하게 다시 적재하도록 프로세스를 구성하는 방법입니다.





보내주신 서버 핵심 코드(index.ts, mining.ts, UserController.ts)를 면밀히 분석한 결과, 어떤 부분에서 시스템의
톱니바퀴가 어긋나 과거 채굴 기록이 유령처럼 남아있게 되었는지 구체적인 원인을 찾았습니다 [1].

개발을 전혀 모르시는 비개발자 눈높이에 맞춰, 두 개의 장부 비유를 통해 원인과 해결책을 아주 쉽게 설명해 드리겠습니다.

1. 아주 쉬운 비유: "은행 진짜 장부"와 "휴대폰 앱 화면"

이 시스템에는 거래 내역을 기록하는 두 개의 서로 다른 장부가 존재합니다.

1.  진짜 블록체인 장부 (코드명: blocks 컬렉션) [1]
      - 은행의 본사 중앙 서버에 기록되는 **'가장 확실하고 안전한 진짜 원본 장부'**입니다.
      - 이번에 테스트 초기화 작업을 하면서, 이 장부에서는 과거 높은 번호의 블록들을 다 찢어버리고 제네시스(0번)와 정상 블록만 남기고
        깨끗이 지웠습니다 [1]. 그래서 전체 블록 수가 31개로 정상 출력되는 것입니다.
2.  지갑 화면용 간이 영수증 함 (코드명: blocktransactions 컬렉션) [1, 2]
      - 사용자가 스마트폰 지갑 앱을 열었을 때, 본사 장부를 처음부터 끝까지 다 읽으려면 로딩이 너무 오래 걸립니다 [1, 2].
      - 그래서 **"해당 유저가 빠르게 볼 수 있도록 영수증만 따로 복사해 모아둔 간이 상자"**입니다 [1, 2].

진짜 문제의 원인

테스트를 초기화하면서 1번(진짜 장부)은 깨끗이 청소했는데, 2번(간이 영수증 함)에 들어있던 과거의 영수증들(74번, 70번 등)은 쓰레기통에
버리지 않고 그대로 방치해 둔 것입니다 [1].

2. 제공해주신 코드에서 찾아낸 "범인" (두 가지 구멍)

개발자가 작성한 코드 안에서 이 쓰레기(구 채굴 기록)가 치워지지 않은 구체적인 구멍 2가지를 짚어드리겠습니다 [1].

구멍 ①: 과거 흔적을 싹 쓸어버리는 "청소기"가 덜 닦였습니다.

코드 중간에 있는 runOneTimeCleanup (일회성 자산 리셋 함수)은 테스트 환경을 완전히 초기화하는 청소기 역할을 합니다 [1].

  - 이 청소기 코드를 보면, 진짜 장부(blocks)에서 번호가 높은 블록들은 시원하게 지우도록 되어 있습니다 [1].
  - 하지만 이 청소기 코드 어디를 봐도, 지갑 화면용 간이 영수증 함(blocktransactions 컬렉션)의 채굴 영수증들을 지우라는
    명령은 쏙 빠져 있습니다 [1]. 본사 서류만 파쇄하고 개인용 영수증 박스는 그대로 둔 셈입니다.

구멍 ②: 자동 수복 엔진(치료사)이 "가짜 영수증을 찢어버리는 법"을 모릅니다.

서버가 켜질 때 작동하는 autoHealBlockTransactions (자동 수복 엔진) 코드를 보겠습니다 [1].

  - 이 치료사는 진짜 장부(blocks)를 쭉 훑어보면서, "어? 간이 영수증 함에 영수증이 빠졌네? 내가 새로 적어줄게!" 하는 추가
    작업만 할 줄 압니다 [1].
  - 반대로 "진짜 장부에는 이미 지워졌는데, 왜 간이 영수증 함에는 여전히 영수증이 남아있지? 이건 유령이니까 지워야겠다!" 하고 삭제하는
    로직이 아예 없습니다 [1].

3. 해결을 위한 처방전 (개발자에게 전달할 내용)

이 문제를 완벽히 해결하려면 개발자에게 아래와 같이 조치해 달라고 요청하시면 됩니다. 비개발자 관점에서도 이해할 수 있도록 쉽게 정리했습니다.

조치 사항 1: 리셋(청소)할 때 간이 영수증 함도 같이 비우기

초기화 함수인 runOneTimeCleanup이 실행될 때, 지갑용 장부(blocktransactions)에 있는 모든 일반 채굴
기록(type: 'Minting')도 함께 일괄 삭제하도록 코드 한 줄을 추가해야 합니다 [1, 2].

  - 개발자 전달용 피드백:
    runOneTimeCleanup 함수 내부에서 blocktransactions 컬렉션의 type: 'Minting' 데이터를 다
    지워주거나 전체 드랍 후 복원해 주세요 [1, 2].

조치 사항 2: 수복 엔진에 "유령 영수증 파쇄" 로직 추가하기

서버가 켜지면서 수복을 할 때, 진짜 장부(blocks)에 존재하지 않는 높이의 채굴 트랜잭션이 간이 장부(blocktransactions)에
있다면 자동으로 삭제하도록 기능을 추가해야 합니다 [1, 2].

  - 개발자 전달용 피드백:
    autoHealBlockTransactions 함수가 실행될 때, 진짜 blocks 컬렉션에 존재하지 않는 blockHeight를 가진
    type: 'Minting' 트랜잭션을 blocktransactions에서 삭제(Clean-up)하는 로직을 추가해 주세요 [1, 2].

4. 요약

  - 현재 상황: 메인 화면의 블록 수(31개)는 진짜 장부를 봐서 정상인데, 지갑 안의 블록 트랜잭션 리스트는 간이 영수증 함을 보기 때문에
    예전 쓰레기 데이터가 보이고 있습니다 [1, 2].
  - 이유: 리셋 코드가 진짜 장부만 청소하고 간이 영수증 장부는 건드리지 않았으며, 수복 엔진 또한 유령 데이터를 찾아내 지우는 능력이 없기
    때문입니다 [1].
  - 해결책: 청소할 때 간이 영수증 장부도 함께 비우고, 수복 엔진이 진짜 장부에 없는 유령 채굴 내역을 알아서 지우도록 코드를 조금만
    보완하면 됩니다 [1].





진지하게 서비스 안정성을 고민하시는 질문자님의 우려를 깊이 공감합니다. 말씀하신 대로 유저들 중에는 채굴을 전혀 하지 않고 추천인 가입만 한
사람도 있을 것이고, 반대로 추천인 가입은 안 하고 채굴만 한 사람, 혹은 둘 다 한 사람 등 다양한 케이스가 얽혀 있을 것입니다.

가장 중요한 핵심은 **"원본 데이터인 '추천 보너스 명부'나 '회원 가입 정보'는 단 1바이트도 건드리지 않고(절대 피해 없이), 오로지
꼬여버린 '지갑 화면용 영수증 장부'만 칼로 수술하듯 정밀하게 청소하고 맞추는 것"**입니다 [1, 2].

비개발자이신 질문자님께서도 흐름을 100% 장악하고 개발자에게 명확하게 지시할 수 있도록, "원본 대조 재작성(Surgical Rebuild)"
방식의 정밀 수복 계획을 단계별로 설명해 드리겠습니다.

1. 세 개의 책으로 이해하는 정밀 수복 개념

이번 작업에서는 데이터를 세 가지 책으로 나누어 다룹니다.

1.  [책 ①] 원본 추천 명부 (절대 수정 금지 / 읽기 전용) [1]
      - 데이터베이스의 bonusrecords 컬렉션과 User 가입 정보입니다 [1, 2].
      - 여기에는 "누가 누구를 초대했는지", "누가 추천인 코드를 넣고 가입했는지" 진짜 원본 기록이 담겨 있습니다 [1, 2].
      - 이 책은 절대 수정하거나 지우지 않고, 오직 '대조용'으로만 읽기(Read-Only)만 수행합니다 [1].
2.  [책 ②] 원본 채굴 대장 (절대 수정 금지 / 읽기 전용) [1]
      - 실제 블록체인 노드가 검증한 진짜 블록 기록(blocks 컬렉션)입니다 [1].
      - 어떤 유저가 실제로 채굴을 몇 번 해서 몇 개의 진짜 블록을 만들었는지 적혀 있습니다 [1].
      - 이 책 또한 건드리지 않고 오직 읽기만 합니다 [1].
3.  [책 ③] 지갑용 임시 영수증 책 (수술 대상 / 삭제 후 재작성) [1, 2]
      - 문제가 발생한 지갑 화면용 블록 트랜잭션 기록(blocktransactions 컬렉션)입니다 [1, 2].
      - 여기에 과거 테스트 잔재나 오류로 인한 유령 블록들이 섞여 있으므로, 오직 이 책만 깨끗이 지우고 위의 1번과 2번 책을 대조하여
        정확한 영수증만 다시 작성합니다 [1].

2. 구체적인 단계별 수복 흐름 (Surgical Repair Step)

서버가 켜지거나 수복 작업을 명령했을 때, 시스템이 각 유저별로 아래의 4단계 공정을 거치게 만듭니다.

[1단계] 기존 꼬인 영수증 책 정리

  - 수복 대상 유저의 지갑 주소를 기준으로, 지갑용 영수증 책(blocktransactions 컬렉션)에 기록되어 있던 해당 유저의 기존
    영수증들을 전부 삭제합니다 [1, 2].
  - 이때 원본 데이터인 User 테이블이나 bonusrecords 테이블은 전혀 건드리지 않으므로, 유저의 가입 정보나 추천 구조에는 아무런
    영향(피해)이 가지 않습니다 [1, 2].

[2단계] 진짜 채굴한 만큼만 영수증 적기 (채굴 기록 수복)

  - **[책 ② 원본 채굴 대장]**을 열어, 이 유저가 채굴자로 참여해 실제로 만들어낸 진짜 블록이 몇 개인지 개수를 셉니다 [1].
  - 예시 A: 채굴을 한 번도 안 한 유저라면 ➡️ 채굴 영수증을 작성하지 않고 넘어갑니다.
  - 예시 B: 진짜 채굴 블록이 3개 존재하는 유저라면 ➡️ 그 3개에 해당하는 블록 번호(예: #15, #17, #21)로 채굴
    발행(Minting) 영수증 3장만 깔끔하게 기록합니다 [1].

[3단계] 내가 추천인 코드를 넣고 가입한 영수증 적기 (자식 가입 보상 수복)

  - **[책 ① 원본 추천 명부]**를 열어, 이 유저가 가입할 때 다른 사람의 추천 코드를 입력했는지(referrerCode 유무)
    확인합니다 [1, 2].
  - 추천 코드를 넣고 가입한 이력이 명확히 존재한다면 ➡️ 가입 보상 전용 가상 높이인 #200000 번으로 추천 보상(Referral
    Reward) 영수증 딱 1장만 기록합니다 [1, 2]. (추천인 없이 가입한 유저라면 적지 않고 패스합니다.)

[4단계] 내가 초대한 사람 수만큼만 영수증 적기 (부모 초대 보상 수복)

  - **[책 ① 원본 추천 명부]**를 열어, 이 유저가 초대한 자식 유저들의 목록(referralList)을 가져옵니다 [1, 2].
  - 자식 목록에 등록된 인원이 정확히 몇 명인지 셉니다.
  - 예시: 자식 목록에 실제 가입 완료된 유저가 5명 적혀 있다면 ➡️ 가상 블록 번호 #100000부터 시작해서 딱 5장(100000 ~
    100004)의 초대 보상 영수증만 순서대로 작성합니다 [1, 2].
  - 주의: 이 유저가 초대한 자식이 또 자식을 초대한 다단계 형태의 데이터는 원본 추천 명부의 내 리스트(referralList)에 들어있지
    않으므로, 자연스럽게 오직 나의 직계 자식 5명에 대한 보상만 오차 없이 기록됩니다 [1, 2].

3. 이 방식이 가장 안전하고 확실한 이유

1.  원본 데이터 보존성: 추천인 명부(bonusrecords)나 가입 데이터는 오로지 읽기만 하고 수정하지 않기 때문에, 가입 상태가
    꼬이거나 추천 보너스 정보가 유실될 위험이 전혀 없습니다 [1].
2.  동적 일치성: 유저가 이전에 채굴을 많이 돌렸든, 채굴을 아예 안 했든 상관없이 오로지 **"실제 블록체인에 저장된 진짜 블록 수"**와
    **"내 추천 리스트에 있는 자식 수"**를 기준으로만 화면용 장부를 새로 그리기 때문에, 수치적 오차가 발생할 여지가 없습니다
    [1, 2].
3.  유령 데이터 차단: 과거 테스트 도중 꼬여서 발생했던 정체불명의 옛날 채굴 데이터나 중복 가산된 오류 블록들은 1단계에서 싹 청소된 후
    원본 대조본으로만 채워지므로 깨끗하게 사라집니다 [1].

4. 개발자에게 전달하시면 되는 명확한 개발 가이드

이 계획을 개발자에게 전달하실 때 아래의 텍스트를 그대로 복사해서 전달하시면 개발자가 정확하게 의도를 이해하고 깔끔하게 구현할 수 있습니다.

[개발 요청 사항: BlockTransaction 정밀 수복 엔진 개선]

현재 blocktransactions 컬렉션에 과거 테스트 잔재 및 중복 가산된 채굴/추천 가상 블록 오류가 남아있는 유저들이 존재합니다. 기존
추천 보너스 원본 장부(bonusrecords)나 유저 스키마(User)에는 어떠한 쓰기(Write) 작업도 수행하지 않고, 오직 이 원본들을
**'읽기 전용(Read-only)'**으로 대조하여 blocktransactions 장부만 안전하게 재구축(Rebuild)해야 합니다
[1, 2].

수복 로직 프로세스:

1.  수복 대상 유저별로 기존 blocktransactions 내역을 일괄 삭제합니다 [1, 2].
2.  진짜 블록체인 장부(blocks 컬렉션)를 조회하여, 해당 유저가 validator로 참여해 생성한 실제 물리 블록 개수만큼만 type:
    'Minting' 트랜잭션을 새로 작성합니다 [1].
3.  User 컬렉션에서 해당 유저가 추천 코드를 기입하고 가입했는지 여부를 판별하여, 조건 충족 시 가상 높이 200000으로 가입 보상
    type: 'Referral Reward' 1건을 재작성합니다 [1, 2].
4.  bonusrecords 컬렉션에서 해당 유저의 referralList 배열 길이를 조회하여, 실제 매핑된 직계 자식 명수만큼만 가상 높이
    100000 + idx로 추천 보상 type: 'Referral Reward' 트랜잭션들을 재작성합니다 [1, 2].

이와 같이 원본 데이터를 기준으로 매 재기동 또는 수복 명령 시 '지갑용 트랜잭션 컬렉션'만 완전한 대조본으로 갱신하도록 처리해 주세요 [1].





제가 상황을 제대로 짚지 못하고 혼선을 드려 정말 죄송합니다.

말씀하신 대로 현재 모든 유저의 채굴 포인트는 완전히 0으로 초기화되었기 때문에, 일반적인 채굴 발행(Minting) 기록을 찾아 복구하는
작업은 아무런 의미가 없다는 점을 명확히 이해했습니다.

현재 유통되는 30 BW 전체가 100% '부모/자식 간의 추천 관계'로만 발행된 보상이므로, 지갑 트랜잭션 내역에서도 일반 채굴
발행(Minting) 기록은 완전히 사라져야(0건) 하며, 오로지 추천 보상(Referral Reward) 영수증으로만 30 BW가
채워져 있어야 정상입니다 [1]. 잘못 이해한 논리로 혼동을 드려 거듭 사과드립니다.

1. 스크린샷 내 "추천 보상을 조회/체크하는 파일" 구분

제공해주신 파일 목록 이미지 중에서 추천 보상 및 추천 관계 데이터를 조회(체크)하거나 다루는 파일들을 목적에 따라 명확히 분류해 드립니다
[2].

① 순수 조회 및 상태 검증용 파일 (Check / Debug)

  - check_bonus_record.js [2]
      - 추천인 보너스 원본 장부인 bonusrecords 컬렉션의 데이터를 직접 조회하고 검증하기 위한 가장 대표적인 조회 파일로
        보입니다 [2].
  - check_bonus.js [2]
      - 지급된 보너스 수량이나 상태를 부분적으로 조회하는 검증 파일입니다 [2].
  - check_referral.js [2]
      - 유저 간의 추천 코드 연결 관계(부모/자식 관계)와 추천 인원수를 조회하여 체크하는 파일입니다 [2].
  - check_real_data.js [2]
      - 실제 DB에 들어있는 실데이터들의 정합성을 전반적으로 체크하는 파일입니다 [2].

② 수복 및 데이터 수정용 파일 (Repair / Fix)

  - repair_rewards.js [2]
      - 잘못 적재되었거나 누락된 추천 보상(Rewards) 데이터를 안전하게 수복하기 위해 만들어진 파일로 추정됩니다 [2].
  - repair_referral_sync.js [2]
      - 부모와 자식 간의 추천인 관계 동기화 상태를 정상적으로 맞춰주는 수복 파일입니다 [2].
  - fix_bonus_record.js / fix_bonus_final.js [2]
      - 정합성이 깨진 보너스 장부 기록을 수정하거나 최종 확정 짓는 복구 파일입니다 [2].
  - fix_referral_codes.js / fix_referral_final.js [2]
      - 추천 코드 매핑 및 관계 오류를 최종적으로 수정하는 파일입니다 [2].
  - force_update_referral.js / manual_process_referral.js [2]
      - 자동 시스템 오류 시 수동 또는 강제로 추천인 관계와 보상을 업데이트하기 위해 작성된 유틸리티 파일입니다 [2].

2. 채굴 포인트 "0" 기준의 올바른 수복 방향

지적해주신 대로 현재 채굴 포인트가 완전히 0인 상태이므로, 블록 트랜잭션 탭의 수복 계획은 매우 명료하고 정확해야 합니다 [1].

  - 진짜 채굴(Minting) 영수증 완전 폐기:
      - 현재 채굴로 인한 블록 발행은 없으므로, blocktransactions 컬렉션 내에서 type: 'Minting'으로 분류된
        모든 트랜잭션 기록은 존재해서는 안 되는 데이터입니다 [1, 2]. 수복 시 이를 전부 무조건 지워야 합니다 [1].
        (이렇게 하면 화면에 남았던 과거 #74, #70 등의 유령 채굴 내역이 완벽히 해결됩니다.)
  - 오직 추천 보상(Referral Reward)으로만 30 BW 구성:
      - 원본 추천 보너스 내역(bonusrecords)에 들어있는 관계들만 100% 신뢰하여, 부모 초대 보상(가상 높이 100000
        ~)과 자식 가입 보상(고정 가상 높이 200000) 트랜잭션만 blocktransactions에 한 땀 한 땀 기록합니다
        [1, 2].
      - 이렇게 만들어진 트랜잭션들의 수량 합계가 정확히 30 BW로 일치하도록 정비합니다 [1].

개발자가 작업을 진행할 때, 스크린샷에 표시된 check_bonus_record.js(조회용)로 원본 데이터를 검증한 후,
repair_rewards.js(수복용) 등을 활용하여 blocktransactions 컬렉션의 '채굴 발행' 내역을 전량 제거하고 '추천
보상'만 원본에 맞게 정밀 구축하게 만들면 안전하게 해결됩니다 [1, 2].





네, 정확하게 파악하셨습니다. 말씀해 주신 핵심이 100% 맞습니다.

현재 채굴 포인트가 0이기 때문에, 해결책은 **"지갑 화면용 간이 영수증 함(blocktransactions)에 몰래 남아있는 '채굴
발행(Minting)' 영수증들만 쏙 찾아서 찢어버리는(삭제하는) 것"**이 전부입니다 [1, 2].

이 작업을 수행하면 추천 보상 영수증(6장)만 깨끗하게 남아 지갑 화면이 정상적으로 돌아옵니다 [2].

비개발자이신 질문자님께서 데이터베이스 관리 프로그램(예: MongoDB Compass)을 이용해 직접 마우스 클릭 몇 번으로 안전하게 처리하실
수 있는 방법과, 개발자에게 전달해 한 번에 끝낼 수 있는 명령어 두 가지로 나누어 정리해 드리겠습니다.

방법 ①: 데이터베이스 관리 프로그램(MongoDB Compass)으로 직접 클릭해서 지우기

가장 시각적이고 안전하며, 코딩을 전혀 몰라도 마우스 클릭만으로 해결할 수 있는 방법입니다.

1.  MongoDB Compass 실행 및 접속
      - 서버 데이터베이스에 접속하는 프로그램인 MongoDB Compass를 실행하고 접속(Connect)합니다.
2.  bitwish_network 데이터베이스 선택
      - 좌측 목록에서 진짜 블록체인 데이터가 담긴 bitwish_network 데이터베이스를 클릭해 들어갑니다.
3.  blocktransactions 컬렉션(장부) 선택
      - 그 아래 세부 목록에서 지갑 화면용 장부인 **blocktransactions**를 클릭합니다 [2].
4.  검색창에 필터 입력
      - 화면 상단에 있는 Filter 입력창에 아래 내용을 그대로 복사해서 붙여넣고 오른쪽에 있는 Find 버튼을 누릅니다.
      - 입력할 내용:
        { "type": "Minting" }
      - 이 작업을 하면 화면에 구 채굴 흔적들(예: #74, #70 등 'type'이 'Minting'으로 되어 있는 영수증들)만
        필터링되어 쭉 나타납니다 [1, 2].
5.  일괄 삭제 실행
      - 검색창 바로 아래에 있는 Delete 버튼(또는 쓰레기통 아이콘 옆의 화살표를 눌러 Delete all documents
        matching query)을 클릭합니다.
      - 정말 지우겠냐는 경고창이 뜨면 확인을 눌러 삭제합니다.

💡 왜 안전한가요? 이 방법은 오직 type이 "Minting"(채굴 발행)인 임시 영수증들만 타겟팅해서 지우기 때문에, 절대 건드리면 안 되는
추천 보상을 나타내는 Referral Reward 영수증들(6장)과 추천 보너스 원본 내역은 털끝 하나 상하지 않고 안전하게 보존됩니다
[1, 2].

방법 ②: 개발자에게 전달하거나 명령어 창에 복사-붙여넣기 할 명령어

터미널(명령어 입력창)이나 몽고 디비 셸(Mongosh)을 사용하신다면, 아래의 마법의 한 줄 명령어를 복사해서 실행하시면 즉시 정리됩니다.

db.getSiblingDB('bitwish_network').blocktransactions.deleteMany({ type: "Minting" });

  - 해석: bitwish_network 데이터베이스 안에 있는 blocktransactions 컬렉션에서 type이 "Minting"인 모든
    유령 데이터를 한 번에 쓸어 담아 삭제하라는 명령입니다 [1, 2].

3. 작업 완료 후 지갑 화면의 변화 (결과 확인)

이 작업을 마치고 나의 지갑 모달을 다시 열어 [블록 트랜잭션] 탭을 확인해 보시면 다음과 같이 깨끗하게 바뀝니다.

1.  화면 아래쪽에 남아있던 가짜 채굴 발행 영수증들(#74, #70, #69, #65 등)이 목록에서 깔끔하게 제거됩니다 [1, 2].
2.  오직 정당하게 획득한 추천 보상 6개(가입 보상 1개 + 초대 보상 5개)만 리스트에 표시됩니다 [2].
3.  불필요한 페이지 이동 화살표나 잘못 표기되던 블록 트랜잭션 수치가 원래 받아야 할 6개의 보상 블록 수치와 완전히 일치하게 정돈됩니다
    [2].





질문자님의 지적이 완전히 맞습니다. 비개발자 입장에서 대시보드 화면에 버젓이 **‘실시간 현재 BW 발행량: 30’**이 찍혀 있고
지갑에도 6개의 추천 블록이 존재하는데, 제가 단순히 "채굴 포인트가 0이다"라고만 뭉뚱그려 설명한 것은 큰 혼란을 드릴 수
있는 무책임한 설명이었습니다. 깊이 반성하며, 질문자님의 날카로운 지적에 감사드립니다.

질문자님이 제기하신 **"왜 30이 남아있는데 0이라고 하는가?"**에 대한 의문을 완전히 해소해 드리기 위해, 시스템의 진짜 작동 원리를
소수점 단위부터 시작해서 아주 명확하게 처음부터 다시 설명해 드리겠습니다.

1단계: 소수점 채굴 포인트가 "완성된 1 BW 코인"이 되는 원리 (물컵 비유)

이 시스템에서 채굴은 **"물방울을 모아 물컵을 채우는 과정"**과 같습니다 [1].

1.  실시간 채굴 (물방울 쌓기) [1]
      - 유저가 채굴기 버튼을 누르면, 화면에서 소수점 단위로 아주 미세한 포인트(예: 0.0001 BW, 0.0002 BW...)가
        실시간으로 차곡차곡 쌓입니다 [1]. 이 미세한 소수점 단위의 숫자가 바로 **'채굴 포인트(진행 중인
        보상)'**입니다 [1].
2.  1 BW 달성 (물컵이 가득 참) [1]
      - 이 물방울들이 끊임없이 모여서 정확히 **1.00000000 BW**가 되는 순간, 물컵이 가득 차 넘칩니다 [1].
3.  블록 생성 (생수병 한 병 완성) [1]
      - 물컵이 넘치는 그 순간, 시스템은 **"1 BW짜리 완성된 코인 블록 1개"**를 뚝딱 만들어 냅니다 [1].
      - 이것이 명세서에 적힌 **"1 BW 채굴 완료 시마다 채굴 증명 블록이 자동으로 기록됩니다"**라는 규칙의 진짜 의미입니다
        [1].

2단계: 추천 보상 30 BW의 정체 (소수점 없이 바로 준 완제품)

그렇다면 대시보드에 보이는 **"현재 BW 발행량: 30"**은 어떻게 만들어진 것일까요?

  - 추천 가입 절차가 발생하면, 시스템은 소수점 물방울을 모으는 지루한 과정을 거치지 않고, 부모와 자식에게 각각 "1.00000000
    BW짜리 완성된 코인 블록 1개씩"을 즉시 지급합니다 [1, 2].
  - 현재 가입자가 17명이고, 그중 추천 코드를 통해 15쌍의 부자 관계가 맺어져 가입 보상이 지급되었다고 가정해 보겠습니다 [1].
  - 이로 인해 소수점 채굴 없이 이미 완성된 1 BW 코인 블록 30개가 즉시 발행되어 시장에 풀렸습니다 [1].
  - 그래서 대시보드에 **"실시간 현재 BW 발행량: 30 BW"**가 당당하게 찍혀 있는 것입니다 [1]. 이 30 BW는 추천 보상으로
    이미 완벽하게 발행된 **'진짜 자산'**이므로 절대로 사라지지 않습니다 [1].

3단계: "채굴 포인트 초기화"의 진짜 의미 (남아있는 30과 초기화된 0)

그렇다면 테스트 중에 채굴 포인트를 초기화했다는 것은 정확히 무엇을 의미할까요?

  - 초기화된 '0' (진행 중이던 물방울들) [1]
      - 유저들이 채굴기를 돌려서 열심히 모으고 있던 미완성 소수점 포인트(예: 0.45 BW, 0.12 BW 등 아직 1.0 BW가 되지
        못해 블록으로 만들어지지 않은 미완성 물방울들)를 전부 0으로 리셋했다는 뜻입니다 [1].
  - 살아남은 '30' (이미 완성된 생수병들) [1]
      - 추천 보상으로 지급되어 이미 블록체인 상에 완전히 생성되어 고정된 30개의 진짜 블록들은 이 리셋 작업의 영향을 받지 않고 그대로
        살아남았습니다 [1].
      - 이 때문에 대시보드 화면에는 여전히 30 BW 발행 / 31개 생성 블록이 표시되고 있는 것입니다 [1].

4단계: 그렇다면 유저 지갑의 "#74, #70" 유령 블록은 왜 생긴 걸까요?

리셋 작업을 하기 전에, 유저들이 실제로 채굴기를 돌려 소수점이 1.0 BW를 돌파해서 진짜 채굴 블록(예: #74번, #70번 블록)들을
만들어냈던 적이 있었습니다 [1].

1.  진짜 장부(blocks)에서의 삭제 [1]
      - 이번 초기화 과정에서, 개발자는 진짜 장부(blocks 컬렉션)에서 이 채굴 블록들을 깨끗이 지웠습니다 [1].
2.  지갑 간이 영수증 함(blocktransactions)에서의 방치 [1, 2]
      - 하지만, 유저 지갑 화면에 보여주기 위해 복사해 뒀던 간이 영수증 함에서는 이 #74번, #70번 영수증을 폐기하지 않고 그대로
        놔두었습니다 [1, 2].
3.  정합성 불일치 발생 [1]
      - 그 결과, 대시보드는 진짜 장부를 보기 때문에 구 채굴 블록이 사라진 **"30 BW / 31 블록"**을 정상적으로 보여주지만,
        유저의 [블록 트랜잭션] 탭은 간이 장부를 보기 때문에 이미 세상에서 사라진 #74, #70 같은 가짜 채굴 영수증이 버젓이
        노출되는 오류가 발생한 것입니다 [1, 2].

5단계: 최종 해결책 (비개발자 맞춤형 정밀 처방전)

결국 해결해야 할 일은 아주 명확합니다.

현재 실제 채굴로 완성된 블록은 단 1개도 없으며, 발행량 30 BW는 오직 추천 보상으로 만들어진 30개의 블록이 전부입니다 [1].

따라서 지갑의 [블록 트랜잭션] 화면을 깨끗하게 만들기 위해 해야 할 일은 단 하나입니다 [2].

유저들의 지갑 간이 영수증 함(blocktransactions)을 전수 조사하여, 예전에 채굴로 소수점이 모여 완성되었다가 지금은 진짜 장부에서
삭제되어 사라진 구 채굴 발행(type: 'Minting') 영수증들을 전부 폐기(삭제)하는 것입니다 [1, 2].

이 작업을 거치면, 지갑 화면에는 정당한 추천 보상 영수증들만 남게 되어, 대시보드의 30 BW 발행량 수치와 지갑 내부의 보상 기록이 자로 잰
듯 정확하게 일치하게 됩니다 [1, 2].

모든 과정과 인과관계를 뭉뚱그리지 않고 소수점 원리부터 다시 설명해 드렸는데, 제 설명에 가졌던 의문이 완전히 풀리셨기를 바랍니다 [1].





데이터베이스를 만질 때 백업과 실패 시 되돌릴 방법(Rollback)을 가장 먼저 생각하시는 것은 아주 훌륭하고 당연한 자세이십니다. 아무리
간단하고 확실한 명령어라고 해도, 백업 없이 진행하는 것은 절대 금물입니다.

문제가 생겼을 때 비개발자이신 질문자님께서도 10초 만에 100% 원래 상태로 되돌릴 수 있는 가장 확실한 대책 2가지를 알려드리겠습니다.

이 작업을 먼저 수행해 두시면, 설령 삭제 작업을 하다가 컴퓨터 전원이 꺼지거나 데이터가 엉망이 되더라도 아무런 피해 없이 원상복구 할 수
있습니다.

대책 ①: 컴퓨터 바탕화면에 영수증 장부 통째로 저장해두기 (가장 추천)

데이터베이스 관리 프로그램(MongoDB Compass)의 내보내기(Export) 기능을 사용하여, 현재 상태의 모든 트랜잭션 기록을 안전한
파일로 내 컴퓨터에 먼저 저장하는 방법입니다.

[작업 전 백업하는 방법 (5초)]

1.  MongoDB Compass에서 bitwish_network 데이터베이스의 blocktransactions 컬렉션으로 들어갑니다 [2].
2.  화면 상단 탭 메뉴 중 Export Collection (또는 Collection 메뉴의 Export) 버튼을 클릭합니다.
3.  옵션 창이 뜨면 Export entire collection (전체 내보내기)을 선택합니다.
4.  파일 형식을 **JSON**으로 선택하고, 파일명을 blocktransactions_backup.json으로 지정하여 바탕화면에
    저장합니다.

💡 이 백업의 장점: 바탕화면에 진짜 영수증 장부 복사본 파일이 하나 생기는 것입니다. 무슨 일이 있어도 이 파일만 있으면 언제든 완벽하게
되돌릴 수 있습니다.

[문제 발생 시 원상복구(Rollback) 하는 방법 (5초)]

만약 수복 작업 후 지갑 화면이 이상해지거나 데이터가 날아갔다면, 아래 순서대로 덮어씌우면 끝납니다.

1.  현재 꼬여버린 데이터베이스의 blocktransactions 안에 있는 데이터를 마우스로 전부 지우거나 컬렉션을 비웁니다 (Empty
    Collection).
2.  상단 메뉴에서 Import Data (가져오기) 버튼을 누릅니다.
3.  바탕화면에 저장해 두었던 blocktransactions_backup.json 파일을 선택합니다.
4.  **Import**를 누르면, 백업을 받았던 바로 그 순간의 깨끗한 상태로 완벽하게 되돌아갑니다.

대책 ②: 데이터베이스 안에 임시 복사본 장부 만들어두기 (개발자 스타일)

데이터베이스 내부에 똑같은 장부를 복사해서 이름을 blocktransactions_임시백업으로 하나 더 만들어두는 방법입니다.

[작업 전 백업하는 방법]

MongoDB Compass 하단에 있는 검은색 명령어 창(MONGOSH)에 아래 명령어를 복사해서 붙여넣고 엔터를 칩니다.

db.getSiblingDB('bitwish_network').blocktransactions.aggregate([{ $out: "blocktransactions_backup_today" }]);

  - 설명: 이 명령어를 실행하면 bitwish_network 데이터베이스 안에 현재 상태와 100% 똑같은 쌍둥이 장부인
    blocktransactions_backup_today 컬렉션이 하나 더 만들어집니다.

[문제 발생 시 원상복구(Rollback) 하는 방법]

작업이 실패하면, 현재 꼬인 장부를 지우고 복사해 둔 임시 장부의 이름을 다시 원래대로 바꾸면 됩니다. mongosh 창에 아래 명령어를
붙여넣어 실행합니다.

db.getSiblingDB('bitwish_network').blocktransactions.drop();
db.getSiblingDB('bitwish_network').blocktransactions_backup_today.renameCollection("blocktransactions");

  - 설명: 꼬여버린 장부(blocktransactions)를 통째로 쓰레기통에 버리고, 복사해 두었던 백업
    장부(blocktransactions_backup_today)의 이름을 다시 원래 이름인 blocktransactions로 바꾸어
    원상복구 하는 명령입니다 [2].

요약 및 제안

  - 대책 ①(JSON 파일 백업) 방식이 프로그램 화면에서 눈으로 보면서 마우스 클릭 몇 번으로 할 수 있어 비개발자분들께 가장 직관적이고
    안전합니다.
  - 실행하시기 전에 대책 ①번 방식대로 바탕화면에 .json 백업 파일을 먼저 받아두신 후, 마음 편하게 삭제 및 수복 작업을 진행하시기
    바랍니다.

이중 잠금장치를 해두시는 셈이기 때문에 실패에 대해 전혀 걱정하지 않으셔도 됩니다.

탭(blocktransactions 컬렉션)에는 과거 테스트 중에 생성되었던 가짜 채굴 발행(type: 'Minting') 영수증 기록이
삭제되지 않고 그대로 남아 화면 정합성이 깨지고 있습니다 [1, 2].

원본 추천인 데이터(bonusrecords)나 가입 정보에는 절대 어떠한 영향도 주지 않고, 오직 blocktransactions 컬렉션만
안전하게 정비하기 위해 아래 작성된 안전 수복 스크립트를 적용해 주세요 [1, 2].

요청 사항: 아래 코드로 fix_block_transactions_safely.js 파일을 만든 뒤, 서버에서 node
fix_block_transactions_safely.js로 단 한 번만 실행해 주시기 바랍니다 [2]. 스크립트 내부에 자동 백업 및 예외
처리 로직이 포함되어 있습니다 [1, 2].

2단계: 개발자에게 전달할 안전 수복 스크립트 코드 (복사해서 텍스트로 전달)

const mongoose = require('mongoose');

async function runSafeFix() {
    try {
        // 1. 데이터베이스 연결 설정
        const MONGODB_URI = process.env.MONGODB_URI || 'mongodb://localhost:27017/bitwish_mining';
        await mongoose.connect(MONGODB_URI);
        console.log("🔌 [데이터베이스] 연결에 성공했습니다.");

        const networkDb = mongoose.connection.useDb('bitwish_network');
        const collection = networkDb.collection('blocktransactions');

        // [안전장치 1] 만에 하나 실패할 경우를 대비해, 지우기 전 실시간 백업본(복사 장부) 생성
        console.log("🚨 [1단계] 만약의 사태에 대비해 자동 백업을 시작합니다...");
        const backupCollectionName = `blocktransactions_backup_${Date.now()}`;
        await collection.aggregate([{ $out: backupCollectionName }]).toArray();
        console.log(`✅ 백업 완료! 문제 발생 시 복구용 임시 장부 이름: ${backupCollectionName}`);

        // [안전장치 2] 지우기 전에 삭제될 대상(type: 'Minting')이 몇 개인지 먼저 카운트
        const countToDelete = await collection.countDocuments({ type: 'Minting' });
        console.log(`🔍 [2단계] 삭제 대상인 구 채굴 발행(Minting) 영수증 개수: ${countToDelete}개`);

        if (countToDelete === 0) {
            console.log("ℹ️ 삭제할 가짜 채굴 영수증이 없습니다. 이미 깨끗한 상태입니다. 작업을 안전하게 종료합니다.");
            await mongoose.disconnect();
            return;
        }

        // [본 작업] 구 채굴 영수증 일괄 삭제
        console.log("🧹 [3단계] 지갑용 장부에서 구 채굴 영수증 삭제 작업을 진행합니다...");
        const result = await collection.deleteMany({ type: 'Minting' });
        console.log(`✅ 수복 정비 완료! 총 ${result.deletedCount}개의 잘못된 채굴 영수증이 삭제되었습니다.`);
        console.log(`⚠️ 만약 지갑 화면에 예기치 못한 문제가 생긴다면, 백업본 컬렉션(${backupCollectionName})을 다시 돌려놓으면 즉시 원복됩니다.`);

        await mongoose.disconnect();
    } catch (error) {
        console.error("❌ [수복 실패] 작업 중 에러가 발생하여 안전하게 중단되었습니다:", error);
    }
}

1단계: restore_block_transactions_safely.js 파일 만들기

VS Code 좌측 파일 목록 빈 곳을 우클릭하고 **[새 파일]**을 누른 뒤, 이름을
**restore_block_transactions_safely.js**로 만들고 아래 코드를 그대로 붙여넣어 저장합니다 [2].

const mongoose = require('mongoose');

async function runSafeRestore() {
    try {
        // 1. 데이터베이스 연결 설정
        const MONGODB_URI = process.env.MONGODB_URI || 'mongodb://localhost:27017/bitwish_mining';
        await mongoose.connect(MONGODB_URI);
        console.log("🔌 [데이터베이스] 연결에 성공했습니다.");

        const networkDb = mongoose.connection.useDb('bitwish_network');
        
        // 2. 데이터베이스의 모든 컬렉션(장부) 목록 조회
        const collections = await networkDb.db.listCollections().toArray();
        const collectionNames = collections.map(c => c.name);

        // 3. 백업 장부들만 필터링
        const backups = collectionNames.filter(name => name.startsWith('blocktransactions_backup_'));

        if (backups.length === 0) {
            console.log("❌ [원상복구 실패] 복구할 수 있는 백업 장부를 데이터베이스에서 찾지 못했습니다.");
            await mongoose.disconnect();
            return;
        }

        // 4. 가장 최근에 만들어진 백업 장부 찾기
        backups.sort((a, b) => {
            const numA = parseInt(a.replace('blocktransactions_backup_', '')) || 0;
            const numB = parseInt(b.replace('blocktransactions_backup_', '')) || 0;
            return numB - numA; // 가장 최근 백업이 맨 앞으로 오게 정렬
        });

        const targetBackup = backups[0];
        console.log(`🔍 [복구 대상 식별] 가장 최근 백업 장부를 찾았습니다: ${targetBackup}`);

        // 5. 현재 문제가 생긴 장부를 지우고 백업본으로 덮어쓰기
        console.log("🧹 [1단계] 현재 꼬인 장부(blocktransactions)를 비우는 중...");
        await networkDb.collection('blocktransactions').drop().catch(() => {});

        console.log(`🔄 [2단계] 백업본(${targetBackup})에서 원래 데이터를 복사해 오는 중...`);
        await networkDb.collection(targetBackup).aggregate([{ $out: "blocktransactions" }]).toArray();

        console.log("✅ [원상복구 완료] 성공적으로 작업을 실행하기 바로 직전의 상태로 100% 돌려놓았습니다!");
        await mongoose.disconnect();
    } catch (error) {
        console.error("❌ [복구 실패] 원상복구 중 예기치 못한 오류가 발생했습니다:", error);
    }
}

runSafeRestore();

치시면 됩니다 [2].
