## 실제 블록 생성 조건 코드 추적

30초마다 `autoRestoreMiningStates()` 실행. 각 유저 루프에서:

```
isGlobalCapReached = currentBlockCount(7054) >= targetBlockCount(?)
```

**`targetBlockCount` 계산식** (index.ts L52~75):
```
targetBlockCount = floor(baseMined + totalSettled + totalBonus)
```

**치명적 문제**: 이 계산식에서 `baseMined`는 **DB에 저장된 `accumulatedReward`의 합산**임.

그런데 같은 함수 안에서 L138에서:
```typescript
accumulatedReward: realTimeAmount.toString()  // 방금 증가시킨 값으로 업데이트
```

**이게 순서 문제의 핵심이다:**

```
[틱 1 - 30초]
① currentBlockCount = 7054 읽음
② baseMined = DB accumulatedReward 합산 → 예: 총 7053.8 BW
③ targetBlockCount = floor(7053.8) = 7053
④ isGlobalCapReached = (7054 >= 7053) = TRUE → 블록 생성 차단
⑤ 각 유저 accumulatedReward를 +채굴량으로 DB에 업데이트 저장

[틱 2 - 30초 후]
① currentBlockCount = 7054 읽음 (변화 없음)
② baseMined = DB accumulatedReward 합산 → 이번엔 7054.1 BW (틱1에서 올려놨으니까)
③ targetBlockCount = floor(7054.1) = 7054
④ isGlobalCapReached = (7054 >= 7054) = TRUE → 여전히 차단

[틱 3 - 30초 후]
① currentBlockCount = 7054
② baseMined = 7055.0 BW (드디어 7055 돌파)
③ targetBlockCount = floor(7055.0) = 7055
④ isGlobalCapReached = (7054 >= 7055) = FALSE → 잠금 해제!
⑤ 각 유저 루프 → realTimeAmount >= nextThreshold 조건 체크
```

**여기서 두 번째 치명적 문제 발생:**

틱 3에서 유저 루프 돌 때:
```typescript
const lastThreshold = new Decimal(state.lastBlockRewardThreshold);
const nextThreshold = lastThreshold.plus(1);
if (realTimeAmount.gte(nextThreshold)) { → 블록 생성 }
```

`lastThreshold`는 틱 1, 틱 2에서 이미 이렇게 업데이트됐다:
```typescript
// Cap Guard 잠금 중이어도 기준점은 업데이트
updatedThreshold = realTimeAmount.floor().toString();  // L129
```

**즉, isGlobalCapReached = true라서 블록은 안 만들었는데, threshold는 계속 올렸다.**

## 🔴 이게 실제로 무슨 의미냐

**구체적 시나리오:**

```
유저 A: accumulatedReward = 629 BW, lastThreshold = 629 (이미 설정됨)

블록이 7054개 있고, targetBlockCount = 7053 → isGlobalCapReached = TRUE

[틱마다] 채굴 계속되어 accumulatedReward = 629.05 → 629.1 → ... → 630 BW
[매 틱] threshold = 630 으로 업데이트 (L129, isGlobalCapReached 여부 무관하게)

나중에 targetBlockCount가 7055로 올라 isGlobalCapReached = FALSE 될 때:
lastThreshold = 630 (이미 올라있음)
nextThreshold = 631
realTimeAmount = 630.xxx
→ 630 >= 631? NO → 블록 생성 안 됨!
```

**이게 진짜 버그다.**

`isGlobalCapReached = TRUE`인 동안 **블록은 안 만들면서 threshold는 계속 올려버려서**  
나중에 Cap Guard 풀려도 **nextThreshold를 이미 넘어버린 threshold 때문에 블록이 생성이 안 되는 구간이 발생함.**

## 🔴 결론 — 현재 구조의 근본 결함

**`isGlobalCapReached = true` 동안 threshold를 올리면 안 된다.**

L129 코드:
```typescript
// 상한 락 적용 중이어도 지갑 기준점은 최신 정수로 동기화하여 중복 감지 방지

```

주석에 "중복 감지 방지"라고 써놨는데, 의도는 이해하나 결과적으로:  
→ **Cap Guard 잠금 중 threshold를 올리면, 잠금 풀린 후 해당 구간의 블록이 영구 누락됨**

### 🔴 1. 왜 블록 수와 BW 수량이 계속 튀고 꼬였는가? (진짜 구조적 결함 3가지)

대표님이 바라시는 원칙은 오직 하나입니다:
$$\mathbf{실제\ 지갑에\ 지급된\ BW\ 총량(정수) = 메인넷\ 실제\ 생성\ 블록\ 수\ (1대1\ 완벽\ 일치)}$$

1. **보너스 지급 시 블록 기준점 미동기화 결함**

2. **BW 잔액 없는 '가상 허수 블록' 개별 생성 결함**
   * `UserController.ts` 및 과거 수복 로직에서 추천 관계가 생길 때마다 실제 BW 자산 증분 없이 `100000번대`, `200000번대` 가상 높이 블록을 DB에 별도로 쑤셔 넣었습니다.

3. **단일 중앙 통제 엔진의 부재 (각자 따로 뜀)**
