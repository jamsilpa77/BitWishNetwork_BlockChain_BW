지적해 주신 **3가지 핵심 질의에 대한 근본 원인 기술 분석**과 **정석 아키텍처 레벨의 해결책 설계안**을 상세히 보고드립니다.

## 1. 체인 무결성(Hash Chain Integrity) 파괴 문제 해명 및 정석 연결 방식

### [기존 땜질식 조치의 위험성 분석]
- 기존 조치는 MongoDB의 단순 문서 개수(`countDocuments`)나 외부 오버라이딩 높이로 블록을 덮어써서 밀어 넣었습니다.
- 이 경우 신규 블록의 `previousHash`가 이전 블록의 `hash`와 일치하지 않는 **체인 절단 현상**이 발생하게 되며, 코어 엔진의 `validateBlock()` 실행 시 100% 해시 체인 무결성 에러가 터지게 됩니다.

### [정석 해시 체인 연결 원칙]
- 모든 물리 블록은 반드시 이전 블록의 암호화 해시(`previousHash`)를 100% 포인터로 가리켜야 합니다:
  $$\text{Block}_{N+1}.\text{header}.\text{previousHash} \equiv \text{Block}_{N}.\text{hash}$$
- 코어 엔진의 `addBlock()`에서 다음 3대 무결성 검증을 100% 통과한 정품 블록만 DB 및 체인 메모리에 승인 적재됩니다:
  1. **높이 완벽 순차 연결**: $\text{Height}_{N+1} = \text{Height}_N + 1$
  2. **이전 해시 완벽 일치**: $\text{previousHash}_{N+1} = \text{Hash}_N$
  3. **PoW 난이도 및 머클 루트 100% 무결점 통과**

## 2. 상태 관리(State Management) 근본 시초 및 동시성 이슈 분석

### [근본 원인: 코어 메모리와 DB간 상태 이원화]
1. **서버 구동 시점의 이원화**:
   - 서버 재시작 시 `BitWishBlockchain.initialize()`가 DB의 `blocks` 컬렉션을 읽어올 때, 메모리 맵(`this.blocks`) 및 현재 높이(`this.currentBlockHeight`)가 완벽하게 복원되지 못했습니다.
   - 이로 인해 메모리 상의 `currentBlockHeight`와 DB의 실제 최고 블록 높이가 어긋나는 동기화 이원화 현상이 시초였습니다.
2. **동시성 이슈 (Race Condition)**:
   - `countDocuments({})`는 동시성 채굴 호출 시 동일한 숫자를 읽어 중복 블록 높이를 생성하는 동시성 장애를 유발합니다.

async createBlockWithPrevHash(validatorAddress: string): Promise<BitWishBlock> {

## 🔴 4대 근본 원인 (Root Cause) 정밀 분석

### 원인 1 — `auditAndSyncGlobalBlocks()` 루프 내 재귀 Cap Guard 조기 차단
**파일**: [`BlockMiningService.ts`](file:///c:/BitWishNetwork_BlockChainMainnet/BitWishNetwork_MiningSystem/server/services/BlockMiningService.ts#L314-L329)

```typescript
// [현재 문제 코드]
if (targetBlockCount > currentBlockCount) {
    const blocksToCreate = targetBlockCount - currentBlockCount;
    for (let i = 0; i < blocksToCreate; i++) {
        await this.onMiningBlock(systemValidator);  // ← 매번 Cap Guard 재실행!
    }
}
```

→ `onMiningBlock()` 내부에서 매번 `_maxAllowedBlocks`를 재산출합니다.  
→ `liveBoost`는 `Date.now() - lastSyncTime`으로 계산되는데, **루프가 돌수록 `Date.now()`가 변해** `_maxAllowedBlocks`가 변동됩니다.  
→ 운이 나쁘면 루프 절반에서 Cap Guard가 `_currentBlockCount >= _maxAllowedBlocks`를 만족시켜 **나머지 블록 생성을 조기 차단**합니다.

**수복 방향**: `auditAndSyncGlobalBlocks()`에서 계산한 `blocksToCreate`를 기준으로, `onMiningBlock()` 대신 **DB 직접 블록 적재(직통 저장) 루프**를 실행하거나, **루프 시작 전 1회만 Cap Guard를 실행하고 루프 내부에서는 직접 블록 생성만 수행**합니다.

**파일**: [`SettlementWorker.ts`](file:///c:/BitWishNetwork_BlockChainMainnet/BitWishNetwork_MiningSystem/server/cron/SettlementWorker.ts#L36-L42)

**수복 방향**: `onMiningBlock()`에서 `createBlock()` 호출 전 **DB의 직전 블록 해시를 읽어 메모리에 삽입**하여 진짜 체인 연결을 복원합니다.

### 원인 4 — `liveBoost` 과대 계산으로 인한 블록 과잉/과소 생성
**파일**: [`BlockMiningService.ts`](file:///c:/BitWishNetwork_BlockChainMainnet/BitWishNetwork_MiningSystem/server/services/BlockMiningService.ts#L46-L57)

`lastSyncTime`이 오래된 유저는 `elapsed`가 수천 초가 되어 `liveBoost`가 비정상적으로 커질 수 있습니다.

**수복 방향**: `liveBoost` 최대치를 `currentTotalRate / 3600 * 제한초(예: 3600초)`로 캡핑하여 이상값 방지.
