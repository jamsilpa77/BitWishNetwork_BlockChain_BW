## 🔴 4대 근본 원인 (Root Cause) 정밀 분석

### 원인 1 — `auditAndSyncGlobalBlocks()` 루프 내 재귀 Cap Guard 조기 차단
**파일**: [`BlockMiningService.ts`](file:///c:/BitWishNetwork_BlockChainMainnet/BitWishNetwork_MiningSystem/server/services/BlockMiningService.ts#L314-L329)

```typescript
// [현재 문제 코드]
if (targetBlockCount > currentBlockCount) {
    const blocksToCreate = targetBlockCount - currentBlockCount;
    for (let i = 0; i < blocksToCreate; i++) {
        await this.onMiningBlock(systemValidator);  // ← 매번 Cap Guard 재실행!
    }
}
```

→ `onMiningBlock()` 내부에서 매번 `_maxAllowedBlocks`를 재산출합니다.  
→ `liveBoost`는 `Date.now() - lastSyncTime`으로 계산되는데, **루프가 돌수록 `Date.now()`가 변해** `_maxAllowedBlocks`가 변동됩니다.  
→ 운이 나쁘면 루프 절반에서 Cap Guard가 `_currentBlockCount >= _maxAllowedBlocks`를 만족시켜 **나머지 블록 생성을 조기 차단**합니다.

**수복 방향**: `auditAndSyncGlobalBlocks()`에서 계산한 `blocksToCreate`를 기준으로, `onMiningBlock()` 대신 **DB 직접 블록 적재(직통 저장) 루프**를 실행하거나, **루프 시작 전 1회만 Cap Guard를 실행하고 루프 내부에서는 직접 블록 생성만 수행**합니다.

### 원인 2 — 중복 실행 락 없음 → 10초마다 중복 실행 충돌
**파일**: [`SettlementWorker.ts`](file:///c:/BitWishNetwork_BlockChainMainnet/BitWishNetwork_MiningSystem/server/cron/SettlementWorker.ts#L36-L42)

```typescript
// [현재 문제 코드]
setInterval(async () => {
    await BlockMiningService.syncGlobalBlocks();  // 실행 중인지 체크 없이 10초마다 실행
}, 10000);
```

→ `syncGlobalBlocks()`가 수백 개 블록을 생성하는 데 10초 이상 걸리면,  
→ 다음 인터벌이 동시에 실행되어 같은 블록 카운트로 두 루프가 병렬 실행됩니다.  
→ **DB 블록 충돌, 블록 높이 중복, 이전 블록 해시 불일치** 등으로 체인 무결성이 깨집니다.

**수복 방향**: `isRunning` 플래그로 단일 실행 보장 (동시 실행 완전 차단).

### 원인 3 — `createBlock()` 메모리 체인 의존성 (5차에서 우회 처리)
**파일**: [`BitWishBlockchain.ts`](file:///c:/BitWishNetwork_BlockChainMainnet/BitWishNetwork_BlockChain/src/engine/BitWishBlockchain.ts#L284-L327)

현재 5차 수복으로 `console.warn + 강제 동기화`로 우회하지만,  
실제 `previousHash` 체인 연결 없이 블록이 저장되므로 **체인 검증 시 전체 실패 위험**.

**수복 방향**: `onMiningBlock()`에서 `createBlock()` 호출 전 **DB의 직전 블록 해시를 읽어 메모리에 삽입**하여 진짜 체인 연결을 복원합니다.

### 원인 4 — `liveBoost` 과대 계산으로 인한 블록 과잉/과소 생성
**파일**: [`BlockMiningService.ts`](file:///c:/BitWishNetwork_BlockChainMainnet/BitWishNetwork_MiningSystem/server/services/BlockMiningService.ts#L46-L57)

`lastSyncTime`이 오래된 유저는 `elapsed`가 수천 초가 되어 `liveBoost`가 비정상적으로 커질 수 있습니다.  
반대로 방금 동기화한 유저는 `liveBoost≈0`이 됩니다.  
→ 두 가드(`onMiningBlock`과 `auditAndSyncGlobalBlocks`)가 동시에 다른 `_maxAllowedBlocks`를 산출하여 **불일치 발생**.

**수복 방향**: `liveBoost` 최대치를 `currentTotalRate / 3600 * 제한초(예: 3600초)`로 캡핑하여 이상값 방지.

# [6차 수복 공정] 2대 원칙(정식 BitWishBlock 역직렬화 & 코어 파이프라인 100% 이행) 완전 수복 작업 공정 계획서

## 개요
외부 senior 개발자의 지적 사항을 100% 수용하여, 기존의 임시 객체(`{ header, hash }`) 주입 및 `replaceOne` raw DB 조작 방식을 전면 제거하고, 블록체인 코어 엔진의 정식 수명주기(Lifecycle) 및 객체지향 역직렬화 원칙을 완벽히 이행하는 초정밀 수복 공정 계획입니다.

## 2대 엄격 이행 원칙

### 원칙 1: DB 역직렬화 시 100% 정식 `BitWishBlock` 클래스 인스턴스 사용
- DB에서 블록 데이터를 읽어 메모리 Map(`bwChainCore.blocks`)에 적재하거나 체인을 동기화할 때, Plain Object(`{ header, hash }`)를 절대 사용하지 않습니다.
- 반드시 `BitWishBlock.fromJSON(blockData)` 코어 정식 역직렬화 static 메서드를 호출하여 완벽한 `BitWishBlock` 클래스 인스턴스(메서드 `calculateHash()`, `isValid()`, `toJSON()` 포함)를 생성한 후 메모리에 적재합니다.

### 원칙 2: Raw DB 조작(`replaceOne`) 및 야매 직통 함수 전면 폐기 & 정식 코어 파이프라인 100% 이행
- `_createSingleBlockDirect()` 및 `BlockMiningService.ts` 내의 Direct `replaceOne` 구문을 전면 삭제합니다.
- 블록 생성은 오직 `bwChainCore.createBlock(walletAddress)` 코어 메서드만 호출합니다.
- `createBlock()` 내부에서 암호학적 머클루트 계산 -> PoW 마이닝(`pow.mineBlock()`) -> 정식 `addBlock()` 체인 연결 -> Engine 내장 `saveToDatabase()` 저장을 100% 거치도록 하여 암호학적 무결성 체인 검증을 100% 통과시킵니다.
- 동시성 충돌 방지를 위해 **순차 바인딩 락(Sequential Promise Lock)**을 도입하여 race condition으로 인한 블록 높이 꼬임을 정식 큐 구조로 해결합니다.
